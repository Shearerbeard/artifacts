Why BIGSERIAL breaks the feed

the fix · option 1 of the grill

One ledger row per sequence

Every append first allocates (seq, txid, IN_FLIGHT) in a small ledger table via its own short transaction. The event insert then marks its row COMMITTED in the same transaction as the event; an abort leaves the row ABORTED — a durable hole marker. The feed advances only over the contiguous prefix of resolved rows.

append path

One append, ledger-first

  1. Allocate. A separate short transaction inserts (seq, txid, IN_FLIGHT) into the ledger. One extra round trip — the cost of the whole scheme.
  2. Write. The event insert uses the allocated seq explicitly (no table default) and marks its ledger row COMMITTED in the same transaction.
  3. Resolve. Commit makes both visible atomically; abort leaves ABORTED behind. There is no state where the event exists but the ledger is wrong.
  4. Feed. Consumers poll the contiguous prefix; delivery is at-least-once with commit-true ordering.
  5. Reap. Ledger rows GC after every consumer cursor has passed them — the ledger is scratch state, not history.
