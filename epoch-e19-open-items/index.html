C3 — feed-path lock waits are unbounded DECIDE

What it is. The feed's poll and ack take the group's cursor row FOR UPDATE with no lock_timeout and no statement_timeout set. A wedged holder stalls that group's feed with no bound.

Why it matters. The write path already has the discipline the feed path lacks. append sets SET LOCAL lock_timeout before taking the funnel (postgres.rs:344), and expiry surfaces as the retryable AppendError::LockTimeout (streams.rs:380). A poll or ack waiting on a held cursor row waits forever. The two paths are asymmetric, and the asymmetry is silent until a consumer group wedges.

Evidence.

  • src/streams/postgres/feed.rs:100 — poll's SELECT ... FOR UPDATE on the cursor row.
  • src/streams/postgres/feed.rs:176 — ack's SELECT ... FOR UPDATE on the same row.
  • src/streams/postgres/feed.rs:14-16 — the module doc: "The row is locked for the transaction's life."
  • src/streams/postgres.rs:169-181 — PgStreamsError has no retryable variant. Adding the bound later means adding one, which is a public type-surface change.
  • src/streams/postgres.rs:344 — the write path's bound, for contrast.

Why the type-surface note matters. The write path classifies a lock expiry as retryable because AppendError has a LockTimeout arm. The feed path returns PgStreamsError, which has no such arm. Bounding the feed wait now is a config line plus a new error arm; bounding it after v1 ships is the same new arm against a published surface, which breaks exhaustive matches downstream.

Options

  • Document "feed waits unbounded in v1" in the ADR and module docs.
  • Apply the write path's bound-and-classify discipline now: SET LOCAL lock_timeout on poll and ack, plus a retryable PgStreamsError variant.

What deciding either way commits you to. Documenting commits you to shipping v1 with unbounded feed waits and a later public type-surface change when you bound them. Applying now commits you to extending PgStreamsError's public surface before v1 and re-reviewing the feed path.

C4 — the wedged funnel holder DECIDE

What it is. lock_timeout bounds each waiter, not the holder. A holder that takes WRITER_LOCK and then goes silent stalls every writer until the server drops the session. The ADR text was already repaired to say this precisely; the code option is a one-line bound beside the existing one.

Why it matters. This is a database-wide write outage, not a per-stream stall. Under the single-writer funnel, one wedged writer blocks every append and every batch, and the lock_timeout that protects waiters does nothing about the holder's tenure.

Evidence.

  • src/streams/postgres.rs:344 — SET LOCAL lock_timeout on the append path; bounds the waiter's attempt.
  • src/streams/postgres/batch.rs:209 — the same on the batch path.
  • src/streams/postgres.rs:77 — DEFAULT_LOCK_TIMEOUT is 5 seconds.
  • docs/adr/0010-allocation-ledger-honest-cursor.md:136-138 — the repaired text: "The bound covers each waiter, not the holder: a holder that goes silent mid-transaction stalls every writer until the server drops its session."

The code option. SET LOCAL idle_in_transaction_session_timeout beside the existing lock_timeout on both write paths. That bounds the holder's tenure — a silent holder gets its session killed by the server after the idle bound — rather than only bounding each waiter's attempt.

Options

  • Apply the one-line code bound now: idle_in_transaction_session_timeout on both write paths.
  • Document the holder risk as accepted, bounded only by the server's session timeout.

What deciding either way commits you to. Applying commits you to a second GUC on both write paths and a re-review. Documenting commits you to accepting a database-wide write outage as the failure mode of a wedged holder, with no crate-level bound on how long it lasts.

C15 — the shipped funnel's own cost was never measured DECIDE

What it is. The spike priced the allocation ledger against per-stream locks. The single-writer funnel that actually shipped was never benchmarked. Its steady-state p99 under saturated writers is inference, not measurement.

Why it matters. The ADR names the trade — serial throughput — but the number itself is a structural argument, not a measured p99. The spike's numbers do not transfer: it measured a design that was superseded.

Evidence.

  • tests/spike_ledger.rs:123 — the unledgered append path takes per-stream advisory locks (pg_advisory_xact_lock(hashtext($1), hashtext($2))).
  • tests/spike_ledger.rs:191 — the ledgered append path takes the same per-stream locks.
  • tests/spike_ledger.rs:11-16 — the harness header: "the spike adjudicated the ledger against the per-stream-lock write path the funnel has since replaced."
  • docs/adr/0010-allocation-ledger-honest-cursor.md:240-246 — "throughput is bounded by one writer's commit latency."

The structural argument (GLM's). At N saturated writers, per-append latency approaches N × one-commit service time. The funnel serializes, so each append waits behind the others. The argument is sound under its assumptions; it is not a measurement.

Options

  • Accept the named trade: the ADR names serial throughput; the exact p99 stays inference.
  • Charter a funnel benchmark: measure the shipped funnel's steady-state p99 under saturated writers.

What deciding either way commits you to. Accepting commits you to shipping v1 with a named-but-unmeasured throughput ceiling. Chartering commits you to a benchmark task before v1, and possibly re-opening ADR 0010 if the measured number is worse than the inference.

C25 — the dormant changelog DECIDE

What it is. AppendError gained a LockTimeout arm — a public API break for exhaustive matches, sanctioned by the card. CHANGELOG.md has been dormant through the redesign and never recorded it.

Why it matters. The changelog's last real entry is 1.0.0-alpha.18, "Prior to Documentation". The Unreleased section has not tracked the redesign, the funnel, or the new error arm. The crate's public history now lives only in git.

Evidence.

  • src/streams.rs:380 — AppendError::LockTimeout(std::time::Duration), the new public arm.
  • CHANGELOG.md:8 — the [Unreleased] section.
  • CHANGELOG.md:72 — the last release entry, [1.0.0-alpha.18] - Prior to Documentation.

Options

  • Revive the convention: log the redesign and the LockTimeout break under Unreleased.
  • Let it lapse deliberately: accept the changelog as stale and the public history as git-only.

What deciding either way commits you to. Reviving commits you to a changelog discipline going forward — every public-surface change logged. Letting it lapse commits you to a stale changelog and no single place that records public API breaks.

The codex-seat deferral DECIDE

What it is. codex FAILed the first fix-review round with one BLOCKING finding: the discriminating funnel test trusted a 300ms sleep to mean "blocked". That finding was verified closed by two different-family reviewers (fable 5.1, GLM 5.3), including empirical pg_locks checks. codex's own updater then deleted its CLI package directory mid-session, and the fallback binary is too old for the pinned model, so its round-3 confirmation seat is deferred.

Why it matters. The 2-of-3 confirmation stands, but the third seat never confirmed round 3. The maintainer decides whether 2-of-3 is enough, or whether the codex seat must be re-run.

Evidence.

  • Card log, 2026-09-07 entry — the fix-round trail: round 1 (fable PASS, codex FAIL on the 300ms sleep, glm FAIL on a minor regression), cc96d02 closed all four, round 2 (both seats FAIL on cosmetics), 5803b97 closed all six, round 3 (fable PASS, glm PASS, codex deferred).
  • src/streams/postgres.rs:702-729 — the pg_locks probe that replaced the 300ms sleep: it observes an ungranted advisory-lock row for WRITER_LOCK, which is what makes the test discriminating rather than decorative.

A note the card flags. This database's catalog lacks pg_blocking_pid (postgres 16.14). The empirical checks used pg_locks, not pg_blocking_pid, so the absence did not affect the confirmation — but the card records it as an anomaly worth investigating outside this card.

Options

  • Accept the 2-of-3 confirmation: fable and GLM, two different families, both verified the BLOCKING finding closed.
  • Reinstall the CLI and re-run the codex seat: restore the codex toolchain and run its round-3 confirmation.

What deciding either way commits you to. Accepting commits you to treating fable + GLM's confirmation as sufficient for the BLOCKING finding and letting Gate U close. Re-running commits you to a CLI reinstall and another review round before Gate U can close.
