Why BIGSERIAL breaks the feed

the fix · option 1 of the grill, hardened by four review rounds

One ledger row per event transaction

Every append or batch first allocates a (first_seq, last_seq, txid, IN_FLIGHT) range from the same sequence object that backs global_sequence — one counter, explicit inserts, column default retired. The allocation critical section (draw, insert, commit) runs under one advisory lock, so rows become visible in first_seq order — that serialization is what makes "a gap below a visible row is burned" a theorem. The event transaction marks its row COMMITTED alongside the events; aborts leave ABORTED — durable hole markers. The feed advances only over resolved ranges in first_seq order.

Orphaned IN_FLIGHT rows (writer died between allocation and append) are reaped by a row-lock protocol, not by transaction-status inspection — an uncommitted claim is invisible under MVCC, so the reaper instead selects old NULL-txid rows FOR UPDATE, re-checks the state, and flips to ABORTED; a late claimer then loses the race loudly through the IN_FLIGHT guard.

append path

One append, ledger-first

  1. Allocate (serialized). Under the advisory lock, a short transaction draws n sequences and inserts the (first_seq, last_seq, NULL, IN_FLIGHT) row. One extra transaction — the cost of the whole scheme, and exactly what the gate-S spike measures.
  2. Write. The event transaction inserts events with explicit sequence values from the range and marks the row COMMITTED in the same transaction (guarded on IN_FLIGHT; zero rows aborts loudly).
  3. Resolve. Commit makes both visible atomically; a caught rollback writes ABORTED. An orphaned row is reaped by the row-lock protocol. No state exists where the events exist but the ledger is wrong.
  4. Feed. Consumers poll resolved ranges in first_seq order; delivery is per-event, at-least-once, with whole-range monotonic acks and one active poller per group.
  5. Reap. Terminal ledger rows GC only behind every group cursor (dead groups are reclaimed by a logged operator action); IN_FLIGHT rows are never GC'd, only reaped.
