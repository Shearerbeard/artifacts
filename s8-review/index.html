The design as built

Every state is one server-rendered page (axum + askama, no client framework). Templates consume tokens.css straight from the design store, so the look cannot drift from the mockups you approved. Light and dark both work. Full frames: the approved mockup set.

1. Card view

"Your chore / What to do" Done

Title, steps in ink circles, checklist graphic, optional video, due line. The stamp is the one action.

2. Done flow

"Mark it done?"

A bottom sheet over the dimmed card. One interruption, not a wizard.

3. Photo upload

"Add photos - 1 to 10"

Grid with previews, remove, counter, inline validation. One multipart post on Finish.

4. Rejected

"Not done yet. Dad says it needs more work."

Notes in the red-edged block. Try again returns to the card.

5. Empty

"Nothing to do yet"

One button: Get my chore. The QR is the URL; no scan step.

6. Moments

"Nice work!" Done / "All caught up"

Approval lands the green ring. Returned-to-pool and empty-pool share the screen family.

Two deltas from the approved set, both flagged at the gate: an awaiting-review variant (after submitting, the card view returns with the stamp disabled; no approved copy exists for a waiting state), and the location line renders only when data exists - the domain has no location field, so it never renders today.

The decisions that carry the risk

Gate A's four rounds landed every finding in this list. If you read code, read these spots.

DecisionWhat shippedWhere
Token is the whole auth modelEvery kid route resolves first; a wrong or absent token is the same bare 404 as a wrong path, so there is no enumeration surface. Fold-on-read: a rotated QR dies on the very next request.token.rs, routes.rs
No sibling data, files includedPayloads derive from the resolved kid and their held card only. A checklist graphic serves when the request path equals the held card's payload path, behind an assignment-ownership guard. Anything else: 404.view.rs, routes.rs
Writes are atomic across two streamsSubmit and approve/reject mirror draw/return: two loads, two decides, one batch. A lost race is a typed retry, never a half-write.coordinator.rs, diffs 02 + 04
Rejection ack is card-scopedThe try-again cookie carries card:version. A later card's first rejection still shows, because short streams reuse version numbers. Caught in round 1.view.rs, routes.rs
LAN-only, enforced in configThe bind address must be private, loopback, or link-local. Wildcard and public addresses fail at startup, with tests on both sides of the line. Caught in round 2.config.rs
Installable, caches nothingPer-token manifest and service worker (start_url and scope are the kid's own URL; Service-Worker-Allowed header so the scope covers it). The worker passes every fetch through - home-wifi-only stands. Rounds 2-3.routes.rs, app.js
Server-rendered, recordedaxum + askama per deliverable 6: the mockups demand no client framework, every state is one page, interactions are form posts plus a thin enhancement script.card log, 2026-08-16

Four review rounds

  1. Round 1 - FAIL, 4 major. Version-only ack cookie, missing assignment guard, silently discarded errors, unregistered service worker. Fixed in 3be7355.
  2. Round 2 - FAIL, 3 major. Worker scope missed the start URL, public-IP binds passed validation, an open /assets mount exposed every graphic. Fixed in d10d094.
  3. Round 3 - FAIL, 1 major + 1 minor. The new graphic route lacked the ownership guard; two stale doc comments. Fixed in a18bff1.
  4. Round 4 - PASS. No findings; both round-3 fixes verified resolved. Reviewer was a different model family from every author, every round.

Your three calls

1. Location. The approved "In the kitchen" line has no data source anywhere in the domain. It renders only if a source ever exists. Source it in S10's augment payload, or drop the line.
2. Awaiting-review copy. After submitting, the kid sees the card view with a disabled stamp and no waiting text - the approved deck has no string for it. Ship as-is, or approve one.
3. Android install. Chromium will not install a PWA over plain LAN HTTP (not a secure context); iOS web clips work today. Pick: self-signed TLS trusted on devices, an HTTPS front, or web-clip-only for V1.
