The gated path — Stage 0 through rollup

  1. Stage 0 — Preflight owner-run · read-only
    On the cube: tailscale version/serve status + the cube's 100.x IP; HTTPS cert check; psql; docker manifest inspect on both images (this decides the pins); firewalld zone check for tailscale0. On the workstation: gh auth, client syncthing versions (all four endpoints must be v2.x).
  2. Stage 1 — Build browser-sync agent · 🛑 user gate
    New private services/browser-sync submodule + shared-infra DB script + ADR-0011. Gates S → A → U: compose config + shellcheck + Vale, a fresh-subagent review where every SYNC_* env var must be cited to upstream docs at the pinned tag, then commit proposals.
  3. Stage 2 — Deploy browser sync + Zen owner-run · 🛑 user gate + user test
    DB init, secrets, compose up, serve on 443, heartbeat checks — then the per-device pref + sign-in. Success: about:sync shows the cube node; a bookmark round-trips; Postgres rows grow.
  4. Stage 3 — Build syncthing agent · 🛑 user gate
    New private services/syncthing submodule (official image layout, .stignore template, README, verify.sh) + ADR-0012 (one-engine decision, git contract, docking rule) + ADR-0008 supersession. Same S → A → U gates.
  5. Stage 4 — Deploy syncthing + onboard clients owner-run · 🛑 user gate + user test
    Cube up (GUI password before serve exposure), discovery/relays off, MagicDNS addresses, two receive-only+versioned folders. Clients: native daemons, .stignore on every device before sharing, mesh pairing. The flip-validation test proves the whole design.
  6. Stage 5 — Rollup agent · 🛑 final review
    server-overview, TODO, CHANGELOG, session log, ADR statuses → accepted. Docs-bustest + Vale clean.
