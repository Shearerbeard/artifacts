crash table

Every crash is a redelivery

Crash pointWhat happens on restartWhy it’s safe
Before the batch append (mid-react)Nothing was written; the feed redelivers the same event.Pure react — no partial state exists.
After the append, before cursor ackEvent redelivered; react runs again; the duplicate intent is rejected.Framework-enforced reaction-key uniqueness returns a typed DuplicateIntent no-op.
Indeterminate batch failure (connection loss, deadlock)Retried, then propagated — never classified as a conflict.Only a confirmed unique-violation with the key present is the duplicate no-op.
Executor: after the Vikunja write, before the done eventIntent redelivered; the HTTP mutation repeats.BoardPort is idempotent + bot-attributed (echo suppression sees it return).
Executor: mutation fails repeatedlyDurable retry budget (derived from failed events) exhausts; intent parks TERMINAL-FAILED carrying the intent key; group advances; compensation hook fires once.Head-of-line blocking is terminal-only; park replay is a no-op.
Executor: crash between parking and ackPark record replays as a no-op append; hook re-fires idempotently.Parking identity = intent key.
Writer dies between ledger allocate and insertRow resolves ABORTED — client-caught rollback, or the row-lock reaper; a late claimer aborts loudly.The ledger’s guarded transitions.
Allocation transaction itself abortsValues burn with no ledger row; the cursor passes them.Serialization makes gaps below a visible row provably burned.
